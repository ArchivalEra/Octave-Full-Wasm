# 求判：把一个大中型 autotools C++/Fortran 数值程序编到 WebAssembly 的三个决策点

> 自足文档：不含任何项目身份信息，只需要你按通用工程判断回答。
> 请只回答「接下来该怎么做」，不需要复述背景。

## 背景（最小必要信息）

- **目标**：把 GNU Octave **11.3.0** 编成能在浏览器里跑的 WebAssembly 产物。
  工具链 **Emscripten / emsdk 5.0.7**（emcc 5.0.7、LLVM 20 世代）。
- **交付形态**：**纯静态托管**（一串静态文件，服务端零计算）。
  由此推出一条硬约束：**产物不能依赖 `SharedArrayBuffer`**，
  否则浏览器要求 cross-origin isolation（COOP/COEP 两个响应头），
  而我们的托管环境给不了自定义响应头。**必须是单线程构建。**
- **已经做到的部分**（供你判断起点，不必再建议这些）：
  - 单线程、非共享内存的构建已成功跑起来，解释器可启动、数值结果与原生同版本逐位一致。
  - 可选编译模块（`.oct`，Octave 的运行时插件）以 **wasm side module** 形式分发，
    运行期 `dlopen` 装载；主模块按可重定位方式链接
    （`MAIN_MODULE=1` + `ALLOW_TABLE_GROWTH=1` + 全树 `-fPIC`）。
    「主模块 + side module 互相解析符号」这条**机制**已用一个最小自造样例验证过（能装载、能回调）。
  - 当前构建的 configure 用的是**最小能力集**：绝大多数可选依赖都是 `--without-*`，
    只有 BLAS/LAPACK、Fortran 运行时（f2c 路线）、正则库是开着的。
  - 那批可选依赖的**源码都在本地磁盘上，不需要下载**。

## 待判的三件事

### 问题 1：验证顺序

可选模块（`.oct`）是整套「按需加载能力」的分发基础。
现在已经验证了 side module 的**机制**，但**没有**验证过
「一个真的、由本树头文件编出来的 `.oct`，能被主模块成功装载并调用」。

同时，「把可选依赖重新开起来」这件事很贵（要先把约 10 个第三方库各自编译到 wasm，
其中若干个还需要 `-fPIC`，然后还要重配、重编整棵树）。

**该先做哪个？**
- (a) 先花小成本编一个**最小 `.oct`**（不依赖任何可选库），确认「真 `.oct` 能被装载」，
  再投入去建那批库。
- (b) 先把可选依赖建起来，最后一起验 `.oct`。

我倾向 (a)：验证成本极小，而它决定了整套分发架构是否成立；
万一不成立，先做 (b) 会让我们在错误的前提下花掉大量时间。

### 问题 2：重新开可选依赖的粒度

旧版本（同一程序的上一个 major）我们有一份**实测可用**的 configure 配方，
是**一次全开**所有可选依赖的。

现在要为 11.x 重新开这批库，有两种做法：
- (a) **一次全开**：照旧配方把库都建好、一次重配、一次重编，然后跑一遍逐库数值断言。
- (b) **一个一个开**：每开一个库就重配一次、重编一次、单独跑该库的数值断言，
  过不了就关回去。

我倾向 (a)，理由是历史证据表明**失败是组合型的**，而不是单库型的：
- 曾经出现过「某个库单独编能过、但最终链接时因 Fortran COMMON 块重复定义而失败」；
- 也出现过「某个 `.oct` 单独编能过、但一装载就因符号签名不匹配而整页崩」。

这两类失败 (b) 的隔离粒度**根本测不出来**。而且 (b) 每开一个库都要一次全树重编，成本高。
如果要保留隔离，我认为**正确的隔离单位是「建库」阶段**（每个第三方库各自 configure+make，
彼此独立、失败可单独定位），而不是「主程序的 configure」阶段。

**这个判断对吗？有没有我没想到的、只有逐库单开才能暴露的失败类型？**

### 问题 3：第三方附加包（Octave Packages / 旧称 Forge）的版本策略

这批附加包是纯 `.m` 脚本 + 少量编译件。旧版本的过滤规则是按包声明的
`depends octave (>= X)` 挑版本，结果是**被迫用较老的版本**
（某个包的新版要求 Octave ≥ 8.1，而当时目标版本更低）。

现在目标升到 11.3.0，这批包可以取**最新版**了。但新版的 `.m` 与编译件是按更新的
Octave API 写的，编译件还得按新版本的头文件重新编译。

**该取最新版，还是刻意先钉在旧版本以降低变量？**
我倾向先钉旧版本跑通、再升版——但如果你认为「能力面」上应该直接取最新
（避免后续再迁移一次），请说明理由。

## 请**不要**建议的方向（这些已实测排除，建议了会浪费时间）

1. **不要建议为 side module 去打开 autotools 的 shared-library 构建。**
   已实测：打开后 configure 会在「需要一个动态链接机制」的探测上直接失败
   （`Octave requires some way to perform dynamic linking.`），而 shared 构建
   对 side module 路线**并非必要**——真正必要的是全树 `-fPIC` + 终链的
   `MAIN_MODULE=1`。
   现在用的是「主程序静态构建 + 把自带的插件目标关掉 + 自己的插件用 side module 单独编」。
2. **不要去改 gnulib 的替代头文件**（例如删掉它生成的 `pthread.h`/`sched.h`）。
   那是为了绕开「如何关掉线程」而人为造出来的第二问题，现已用别的方式解决。
3. **不要建议 `-sSHARED_MEMORY=0` 之类去"洗"一个已经带 `-pthread` 编出来的树**，
   我们已经把线程从 configure 层掐掉了，不需要逆向操作。
