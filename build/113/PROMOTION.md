## 二、阻塞点：稀疏 `lu`（UMFPACK）——**换过去就是功能回退**

逐条实测（`/tmp/nodegrade.log`，两个站点同样 8 个用例）：

| 用例 | 8761（7.2） | 8762（11.3.0） |
|---|---|---|
| `[L,U,P]=lu(s)`（稀疏） | ✅ `full(L*U-P*s)` = `0 0 0 0` | ❌ `error: support …`（UMFPACK 被关） |
| `[L,U]=lu(s)`（稀疏） | ✅ 同样为 0 | ❌ 同样报错 |
| `spparms()` | ✅ | ✅ 一致 |
| `s\b`（稀疏） | ✅ | ✅ 一致 |
| `chol(s)`（稀疏） | ✅ | ✅ 一致 |
| `qr(s)`（CXSparse） | ✅ | ✅ 一致 |
| `eigs(s,2)`（ARPACK） | ✅ | ✅ 一致 |
| `__ode15__` 可用 | ✅ | ✅（且本轮已从桩变真模块）|

**为什么不能直接换**：`AGENTS.md` 的验收底线写着「新实验失败不许让它退化」。
`accept-requirements` 里没有稀疏 `lu` 这一条，所以**光看需求级闸门会漏掉它**——
这正是本次逐条对比才查出来的。

两条路，都要人来定：
- **A（推荐）先修 UMFPACK**：把 UMFPACK 重新开进主链，让 `lu(s)` 在 11.3.0 上可用，
  再换基线。根因目前**未查明**（「索引宽度」假设已被实测证伪，见 `NOTES-umfpack.md`）。
- **B 接受回退**：换基线，并把「11.3.0 上稀疏 `lu` 不可用」写进交付说明当已知偏差。
