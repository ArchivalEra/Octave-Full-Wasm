## 1. 方案 A：不推荐

**理由**：A 和 A2 的挂起/恢复机制完全相同，唯一区别是 A 把 `eval_async` 这个 **embind JS 侧名字**塞进 `JSPI_EXPORTS`。查到的资料里，`JSPI_EXPORTS` 的官方定义是"会调用异步 import 的**导出模块函数**列表"，这是在 wasm 导出表这一层做匹配的设置；而 embind 的 `async()` 参数只是告诉 embind 胶水"这个绑定函数返回值要包一层 Promise"，两者是两套独立的命名/包装机制拼在一起，没有查到明确文档保证二者所指对象一致。

**可证伪判据**：编译后直接用 `wasm-objdump -x`（或 `wasm2wat` 看导出段）核对 `eval_async` 是否是 wasm 导出表里的真实条目名；再检查该导出是否真的被 binaryen 的 JSPI 相关 pass 处理过（对照 A2 产物里 `eval_wait` 的处理结果做差分）。这一步分钟级，不需要跑通交互流程。

**爆炸半径**：0（不采用）。

## 2. 方案 A2：有条件推荐 ★（核心方案）

### 你们要审的核心问题：收窄之后，"上游整条入口都可能挂起"还成立吗？

**结论：机制依然成立，但它是 JSPI 本身的固有语义，不是 dlopen 带来的副作用；收窄不会消除它，只是把"哪些入口需要补标记"变成你们可控的事。**

依据：JSPI 官方文档明确写着——会调用异步 import 的导出**必须**显式列进 `JSPI_EXPORTS`，这本来就是穷举式、非自动传播的机制（这一点和老 Asyncify 的自动探测传播完全不同）。有一个可以直接类比的真实案例：某大型 C++ GUI 框架移植到 wasm 时，把"模态对话框"这类嵌套事件循环做成了一个 JSPI 挂起点，结果发现从 Python 脚本驱动进入时因为走的是被包装成 promising 的入口，一切正常，但从真实鼠标点击驱动的每一个对话框都失败了——因为浏览器 DOM 事件监听器进入 wasm 走的是一个没有被标记为 promising 的 embind 调用，同样的 C++ 代码在触达挂起点时直接抛出 SuspendError，而框架把这个异常吞掉了。这和你们文档里 §2.4① 描述的现象（"上游整条入口都变成可能挂起"）在因果上是一回事：**不是"整条入口都被自动标记"，而是"没被标记的入口一旦真的走到挂起点就会炸"**，收窄之后这个坑没有消失，只是从"到处都在报错方便你发现"变成"只有真的踩到才会报错"，对大型项目反而更危险——因为遗漏的路径可能很久都不会被触发（比如某个很少走的调试分支）。

对 §2.4③（静态初始化期间碰 dlopen）：这条红线有一个几乎同构的真实案例可以直接引用——有人在用 `-sJSPI` 编译一个引入了第三方日志库的大型 C++ 项目时，模块实例化阶段执行到某个全局静态对象的构造函数（调用了 `chrono::steady_clock::now()`）就直接抛出 SuspendError，导致页面永远起不来。这不是 dlopen 特有的问题，而是"任何在 `__wasm_call_ctors`（含 side module 装载时机）阶段执行的、恰好落在被 JSPI 包装的调用图里的代码"都会触发同一个失败模式。**§2.4③ 这条红线成立，而且比你们想的更宽——不限于 dlopen，任何静态初始化都要查。**

对 §2.4②（顺序即机制：先走一次 promising 包装的入口，之后同产物里同步走 dlopen 路就正常）：我没有查到任何规范或 Emscripten 文档把这个"先热身一次就正常"的现象记录为**受支持的契约**，它更像是 V8 实现细节里的懒绑定/缓存副作用。**建议不要把这条当稳定设计依赖**——升级 V8/Emscripten 版本时这个顺序技巧完全可能失效且不会有 changelog 提示。如果要用，应该让"第一次调用必须走正确的 promising 包装"成为架构上的强制顺序（比如在装配完成后自动做一次哑调用预热），而不是依赖"凑巧先调用过一次就好了"。

### 关于收窄实现是否可靠

有一条非常新的证据（2026 年 9 月一个仍在开发中的 Emscripten PR）明确写到：无论设置如何，`invoke_*` 这类 JS 侧调用包装器现在都不再被当作可挂起的对象处理，因为 JSPI 没法跨越它们所在的 JS 栈帧挂起。这和 2023 年那条老 issue 里"`invoke_*` 默认被标记为 JSPI import"的抱怨正好是相反方向的修复——说明这条坑目前处于"官方已经在收紧、但版本新旧行为不一致"的状态。你们用的是 `-fwasm-exceptions`（原生 wasm EH），本来就不太会生成基于 JS 异常的 `invoke_*` 包装器，所以这条坑对你们的实际暴露面可能比看起来小，但**必须用你们自己 5.0.7 的实际产物验证**，不能假设文档描述的最新行为已经在你们这个版本落地。

**可证伪判据（三条）**：
1. 从一个**没有**被列进 `JSPI_EXPORTS` 的同步导出，通过一次间接函数指针调用跳到会执行 `web_pause_ms` 的同一段代码。预期：红——抛 `SuspendError`。这直接量化"未列入的入口保持纯同步"这句话的代价：代价不是"没有"，而是"这类入口一旦真被调用就会崩，而不是优雅降级"。
2. 在一个 side module 的全局构造函数里塞一次任意间接调用（哪怕和 `pause` 完全无关），重新走一遍 dlopen 流程。预期：绿；如果意外变红，就是 VTK 那个案例在你们的 MAIN_MODULE=2 布局下复现，说明 binaryen 的 `--jspi` 相关 pass 顺手包了不该包的东西。
3. 反复调用 `eval_wait` → `dlopen` 一个新 side module → 再调用 `eval_wait`，观察是否需要"先热身"才能稳定，以此证伪/坐实 §2.4② 是否是版本相关的实现细节而非契约。

**爆炸半径**：新增 1 个 JS library 函数 `web_pause_ms`（几行）+ 1 个 `extern "C"` 薄导出 `eval_wait`（几行，内部转调既有 eval 入口）+ 链接行 3 个新 flag。

**第一步最小实验（半天）**：在你们已有的"最小链四件套"探针上加上面两个用例（1 和 2），输入是两段几十行的最小 C 文件 + 一次 dlopen 一个几行代码的 side module，命令就是你们已经跑通的那条链接命令，预期输出按上面写的红/绿标准即可判定。

## 3. 方案 B：有条件推荐（作为 A2 的备选或并行验证对象）

**①规范层面是否成立**：成立。JSPI 的工作方式是拦截从 JS 调用返回的 Promise 对象，挂起 WebAssembly 应用的主逻辑，并在浏览器事件循环调用回调时恢复被挂起的 WebAssembly 代码；同时 WebAssembly 导出被改造为返回一个 Promise 对象而不是原始返回值——这整套描述完全是在**实例化之后**的 JS 反射层面完成的，`WebAssembly.Suspending`/`WebAssembly.promising` 不需要 wasm 二进制里有任何特殊 section，也不需要编译期标记。也就是说，理论上 B 甚至可以完全不加 `-sJSPI` 编译，纯靠你们自己在 `instantiateWasm` 钩子里包一层。

**②对 5.0.7 生成的胶水有没有已知坑**：这一点我没有查到直接针对 "MAIN_MODULE=2 + `instantiateWasm` 手动改 imports/exports" 的公开案例，只能从架构上推理：MAIN_MODULE=2 的 glue 在实例化前后还要做动态链接相关的簿记（`GOT.func`/`GOT.mem` 重定位、side module 的表项 patch 等），如果你们替换了导出引用（用 `promising` 包装后的新函数对象替代原始导出），要格外注意 **side module 是否会通过某个在实例化时缓存下来的旧函数指针**（比如表项里存的还是包装前的引用）绕过你们的包装，导致同一份逻辑在"主模块直接调用"和"side module 反向回调"两条路径上行为不一致。这是 B 相对 A2 多出来的、A2 不存在的一类新风险（A2 是编译期全局替换，不存在"新旧引用并存"问题）。

**③与 A2 相比哪个更稳**：短期看 A2 更稳（走官方支持路径，出问题至少能在 Emscripten issue tracker 里搜到同类），B 更薄但和 5.0.7 这一个具体版本的 glue 实现细节强耦合，升级 emsdk 时几乎肯定要重新走查。建议**先做 A2，把 B 当平行验证/退路**，而不是主推。

**可证伪判据**：在 `instantiateWasm` 钩子里手动实例化，其余 import 原样透传 Emscripten 生成的 importObject，只包一个 `web_pause_ms`；实例化后只把 `eval_wait` 换成 `promising` 包装版本再暴露给页面。用你们的"最小链四件套"探针跑一遍，如果 side module 通过函数指针表回调到这个被替换的导出时行为和 A2 产物不一致（比如挂起失败、或者拿到的是包装前的同步版本），就说明"table 里保存的引用先于你的替换发生"，B 在 MAIN_MODULE=2 下不成立。

**爆炸半径**：0 处 emcc 链接 flag 改动（甚至可以去掉 `-sJSPI`），改动集中在 1 个 JS 胶水文件里的 `Module['instantiateWasm']`（几十行）。

**第一步最小实验（半天）**：把 A2 已经写好的"四件套"探针原样复用，只把 `-sJSPI -sJSPI_IMPORTS=... -sJSPI_EXPORTS=...` 换成手写的 `instantiateWasm` 版本重跑。同一份 C 代码、同一个 side module，唯一变量是包装方式，直接对照 A2 的红/绿结果。

## 5. 方案 D：不推荐，红线维持

SharedArrayBuffer 必须运行在 HTTPS 下（本地开发时 localhost 除外），COOP/COEP 这两个头是用来强制实现跨源隔离的，这是 secure context 层面的硬限制，不是"服务端配置不了响应头"这种可以用 Service Worker 绕过的问题（Service Worker 那类技巧只解决"托管平台不让自定义 header"，前提仍然是这个站点本身跑在 HTTPS 上）。2026 年内没有查到任何针对"非 localhost 纯 http 静态托管"的合规豁免机制或提案。

**可证伪判据**：在目标托管环境里直接读 `self.crossOriginIsolated` 和 `typeof SharedArrayBuffer`；只要是 `false`/`undefined`，红线就还成立。

## 6. 方案 E：留白

**stack-switching 提案现状**：仍处于提案/原型阶段，2026 年的 WebAssembly 年度综述把它列为"跟踪 Wasmtime 里的原型实现"这一类 action item，不是"可用"状态，该提案的定位是通过 continuation 管理多条执行栈，为 async/await、协程、生成器、绿色线程等提供原生支持，2026 年的动作是跟踪 Wasmtime 里的原型实现，没有任何浏览器把它列入近期落地计划。**2026 年内它不构成 JSPI 的替代路径**，只是未来可能替代/补充 JSPI 的方向。

**JSPI 的 spec 稳定性**：Safari 最初对该提案有顾虑、不打算实现，但在 2025 年底撤回了反对意见，提案目前处于 phase 4，phase 4 通常意味着核心 API 形状不会再有破坏性变更。但要注意两点：一是 Safari 到 27 版本才正式支持——JSPI 相关能力在 Safari 27 中被加入支持，其底层改动落地时间是 2026 年 2 月 12 日，晚于 Safari 26 分支点，所以没有随任何 26.x 更新回溯，时间点相当晚近；二是围绕"重入/影子栈"这类高级语义，各引擎和 Emscripten 自己都还在活跃开发中——2026 年 7 月的两个 Emscripten PR（`JSPI reentrancy primitive` 和 `ASYNCIFY_REENTRANT`）都明确标注"暂不合并"，因为在 JSPI 之下，挂起时原生栈会切换，但存在线性内存里的 wasm 影子栈是共享的，导致一个在另一次调用挂起期间被重新进入的 promising 导出可能会破坏被挂起那次调用的栈帧。这条**直接命中你们 §4 要求补充的"重入"测试项**，见下一节。另外 Emscripten 自己在 2026 年 9 月还有一个仍在开发、尚未合并的官方新姿势——`JSPI_HOOKS`/`<emscripten/jspi.h>`，用来让库代码感知"进入/退出/挂起/恢复"这几个 JSPI 生命周期事件，目前仍是实验性、未合并状态。

**其它大型 wasm 解释器/REPL 项目的公开经验**：目前查到的案例集中在图形应用/游戏引擎（前面提到的 GUI 框架、VTK、一款用 miniaudio+sokol 的小游戏引擎），核心教训和你们文档里列的高度一致：漏标一条能到达挂起点的入口就会在那条路径上炸；从 Asyncify 迁移到 JSPI 不是改个 flag 就完事，有开发者把 dosbox 的移植从 Asyncify 换成 JSPI 加 `-fwasm-exceptions` 后，编译能通过，但运行时在一个自旋等待的睡眠调用处直接抛出 SuspendError，最后定位到是某个入口没有被正确包装。**值得一提的是 Pyodide（CPython 的 wasm 移植）和 wasm-bindgen 都在 JSPI 之上自己实现了影子栈切换来解决重入问题**，这从侧面印证了"重入"是这个赛道里公认的硬骨头，Emscripten 官方支持目前还没跟上。我没有查到"大型通用解释器整体迁移到 JSPI"的完整公开案例可以直接参考——你们大概率是这类项目里较早的公开实践者。

## 7. 对 §2 已有结论的意见

1. **Asyncify 死路**：同意，没有查到反例；查到的多个真实迁移案例都是"放弃 Asyncify、改用 JSPI + `-fwasm-exceptions`"的方向，和你们的判断一致。
2. **单产物+运行时能力门可行**：同意，没有查到反例。
3. **最小链四件套成立**：同意，和 JSPI 的基本设计（挂起时事件循环继续跑）一致。
4. **`-sJSPI` 胶水三条机制**：①③同意，但要**修正因果关系**——①不是 dlopen 带来的副作用，而是 JSPI"显式穷举、不隐式传播"的固有语义，收窄不会消除它，只会把它变成你们可控的范围（见 §2 详述）；③成立且比 dlopen 更宽，任何静态初始化期间的间接调用都要查（有 VTK 案例佐证）。②**保留意见**：这更像是 V8/Emscripten 实现细节里的懒绑定副作用，不是受支持的契约，不建议当作架构依赖，建议改为"装配完成后强制预热一次"来规避对这个顺序技巧的依赖。
5. 是现状陈述，无需表态。

§0 红线：不需要抢占式取消/并发解释器/多实例/Worker 化——没有证据反对。COI/SAB 红线——见方案 D，成立。浏览器版本门槛：Chrome ≥137、Safari ≥27 两条我查到的资料吻合；**Firefox ≥153 这一条查到的资料不完全一致**——有的资料显示 Firefox 需要手动打开 flag 才支持（147 版本仍需 `about:config` 开关），也有资料把 139 作为可用起点，各方口径不统一，且各浏览器厂商在 Interop 2026 里承诺"2026 年内跟上"但没有统一给出具体版本号。**建议你们在做兼容性降级判断时用 feature detection（`typeof WebAssembly.Suspending !== 'undefined'`）而不是硬编码版本号**，版本号门槛本身在这几个月内还在变动。

## 8. 补充必测项（挂起 × 异常）

除你们已列的五条外，建议补充：

1. **【高优先级】重入测试**：挂起等待期间，页面上的另一次用户操作触发**同一个** promising 导出（`eval_wait`）被再次调用。这不是假设性风险——Emscripten 官方两个相关 PR 目前都因为"影子栈共享导致后进入的调用会破坏被挂起调用的栈帧"这个问题而处于未合并状态。你们的 REPL 断点调试功能（"进一层交互式子会话"）如果存在"外层调用还挂起着、内层又要发起一次新的 eval"这种场景，**这条必须在半天实验里排进第一优先级**，而不是排在最后。如果你们的实际交互设计能保证"任意时刻只有一条调用链处于挂起状态、不存在嵌套二次进入"，可以规避这个问题，但需要在架构上明确写下这条约束，而不是隐式假设。
2. **静态初始化期间的任意间接调用**（不限于 dlopen 触发）：对应 VTK 的真实案例，主模块自身 `__wasm_call_ctors` 阶段、side module 装载阶段都要各测一次。
3. **table 增长（`ALLOW_TABLE_GROWTH`）与挂起点共存**：dlopen 反复装载/卸载会导致函数表重新分配，验证一个已经被 promising 包装的导出对应的表项在表增长后是否仍然指向正确的包装版本。
4. **挂起期间页面侧对共享状态的写入时序**：不只是验证"页面定时器/动画照常跑"，还要验证 resume 之后 wasm 侧读到的状态（比如队列里堆积的多次鼠标事件）顺序和数量是否符合预期，这条比"动画有没有卡住"更容易出隐蔽 bug。
5. **双向调用链标记**：MAIN_MODULE=2 下，side module 通过函数指针回调进主模块的 promising 导出这个反向路径，是否也需要独立标记验证，不能只测"主模块调 side module"这一个方向。
