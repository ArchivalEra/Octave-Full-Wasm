# 60: **libm 部件插件 spike**：链接期替换 musl 标量超越函数，量"不改 Octave 调用点"的收益上限

**What to build:** 工单 58 盘点出下一个真部件候选 = **libm（重）**：元素级数学热点全是
musl 标量超越函数（各负载里 `exp_inline` 24% / `log_inline` 10% / sin+cos+`__rem_pio2` 51% /
`pow` 15%）。"SIMD 批量 libm + 改 Octave 元素循环批量调用"是**源码级集成**——
与用户拍板"**极其不想脱离 Octave 树**"冲突 ⇒ 本单只量**插件边界内**的上限：
**纯换 libm 实现、Octave 源码一行不改**，每个标量调用本身能快多少。

**Blocked by:** None

**Status:** ready-for-agent

**Settling:** 不存在 —— 本工单的第一交付物（`build/113/bench-libm-spike.sh`：
候选标量实现（SLEEF 纯标量 u10 / musl-express 等）对 musl 现役，单向量 sin/exp/log/pow
微基准，wasm32 + w64 双车道，交错 ≥3 轮；rc=0 且输出对比表 ⇒ 有效数据）。

## 任务（spike 三步）

1. **微基准**：候选实现 vs musl，单向量 sin / exp / log / pow；交错 ≥3 轮
   （本机单轮方差 ±30%，HISTORY §5.79/§5.84 方法论）；量的是**逐调用**加速比。
2. **只对上限 ≥2× 的函数做第二步**：lane-shim / 库序替换（不动 Octave 树，只动链接）→
   `hotpath.py` 复测元素级负载，看热点是否如预期从 musl 移到新实现。
3. **结论进 `build/113/NOTES-libm.md`**：本单唯一的问题 = **"插件边界内能拿到多少"**；
   批量化的真上限需要改 Octave 元素循环 ⇒ 把"批量还能多拿多少"的估算写清（供工单 61
   的硬边界章节引用），但**不立项、不动树**。

## 判据

- 标量替换把元素级负载的 libm 热点压下 **≥1/3** ⇒ 值得注册为插件（走工单 61 的契约）；
- 否则 libm 轴在"不脱离树"约束下**如实否决**（记录进 NOTES，与 49 faer / 51 PGO 同款负判决归档）。

## 边界

- 探针/基准**不进开机路径**；实验产物只进实验站（wasm64-NEXT 分支纪律）；
- SLEEF 等候选是**第三方源码树**引入 ⇒ 就算采纳也要先过"白名单 + 精度验收（数值全绿）+
  体积代价"三关；本单只做测量，不带依赖进产物。
