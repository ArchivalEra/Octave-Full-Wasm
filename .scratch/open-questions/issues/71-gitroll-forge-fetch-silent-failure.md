# GitRoll Issue #7 · 修复 spec —— forge-fetch 静默失败是第一优先

**Status:** ready-for-agent
**Settling:** `python3 build/forge-fetch.py --selftest`
rc=0 ⇒ 全部静默路径已堵（缺包/不兼容/空闭包三种都必须非零退出）
rc=1 ⇒ 还有静默路径
rc=2 ⇒ 读不到（fail-closed）

---

## Problem Statement

用户（构建链的下游）今天面对的现实：**`build/forge-fetch.py` 有包解析不出来时会静默成功。**

`forge-build.sh` 这样调用它：

```sh
python3 "$REPO/build/forge-fetch.py" --octave "$OCTAVE_VER" --dest "$FORGE" $PKGS
```

没有 `set -e`、没有检查退出码，接着就"解包 → 打包成资产"（`tar xzf … || true` 又吞一次错）。
于是**缺包 / 版本不兼容 / 依赖闭包空**的情况全部被当成成功：站点上少几个包，而所有
闸门都是绿的。

GitRoll 把它标成 **BLOCKER**（"Refactor this method to not always return the same value"）。
我第一眼判它是误报（`resolve()` 是副作用递归、本来就返回 None），**用户要求复核后确认
这是真缺陷**：

```
解析出的包: ['a']                    ← 'definitely_missing_pkg' 被跳过
resolve 返回: None                   ← 调用方无从判断"有包没解析出来"
main() 退出码: 0                     ← 下游当作全部成功
```

三条静默路径（实测，每条都只往 stderr 打一行）：

| 路径 | 触发条件 | 现在的行为 |
|---|---|---|
| 索引里没有该包 | `index.get(name)` 为 None | `continue` |
| 没有兼容宿主 Octave 的版本 | `pick_version()` 返回 None | `continue` |
| 闭包解析结果为空 | 所有包都走到上面两条 | `plan == []`，退出 0 |

**最坏情形**：全部包不兼容 ⇒ 脚本打印"解析出 0 个包" ⇒ 退出 0 ⇒ 下游构建出**一个空货架**，
所有闸门绿。

## Solution

让 `forge-fetch` 的失败**响亮且带退出码**，并且把"成功"的定义收紧到"请求的每个包
都在闭包里"：

1. `resolve()` 不再用 `continue` 静默跳过 —— 把失败**收集**进一个结果对象（缺哪些包、
   因何原因：`not-in-index` / `no-compatible-version`），让调用方能处理。
2. `main()` 在有任何未解析项时**非零退出**，并把原因逐条点名；
3. 空闭包（请求了包但 `plan` 为空）**必须非零退出**（零值守卫：空不是成功）。
4. `forge-build.sh` 在 `forge-fetch.py` 非零时**立即停**（不再往下解包/打包）。

## User Stories

1. 作为构建链维护者，我希望缺包时 `forge-fetch.py` 以非零退出，这样 `forge-build.sh`
   不会拿着不完整的货架继续往下跑
2. 作为构建链维护者，我希望错误信息**逐条点名**（哪个包、为什么：不在索引 / 无兼容版本），
   这样我不用翻 stderr 大段输出猜
3. 作为构建链维护者，我希望**版本不兼容**也被当成失败（而不是打一行 warning 继续），
   因为"装了个跑不起来的包"比"没装"更难查
4. 作为构建链维护者，我希望请求了 N 个包但闭包为 0 时**明确失败**，
   因为那意味着整条取包路径已经坏了
5. 作为构建链维护者，我希望 `--list-compatible` 这条只读命令**不受影响**
   （它本来就该 0，且不下载）
6. 作为构建链维护者，我希望失败时**已经下载成功的包保留在缓存里**（不删），
   这样重跑能复用、不会白花带宽
7. 作为审查者，我希望 `resolve()` 的返回值是**结构化的**（不是 None），
   这样"它永远返回同一个值"这条告警从语义上也消失，而不只是被压制
8. 作为审查者，我希望修复带 `--selftest`，三类用例齐备（正常/该报/空输入），
   这样它能证明自己会红
9. 作为下游 `forge-build.sh`，我希望 fetch 失败时**不继续解包**，
   因为半套包解出来会让后续步骤产生更难定位的错
10. 作为用户，我希望这次修复**不改变任何成功路径的输出格式**，
    因为已有脚本可能解析那些行

## Implementation Decisions

- **`resolve()` 改为收集失败**（不是抛异常），失败项以 `{name, cause, why}` 结构
  **收进调用方注入的 list**（`cause` ∈ `not-in-index` / `no-compatible-version`）。
  为什么不用抛异常：递归里有多个包，抛第一个会遮住其余；收集才能一次点名全部。
  ⚠️ 实现选了**出参（out-param）**而不是"返回结果对象"——评审指出这与 spec 原字面
  不完全一致，且 `fail` 若给 `=None` 默认会留一条 fail-open 后门。**结论：保留出参形状，
  但 `fail` 是必填**（忘了传就跑不起来，而不是静默回到旧行为）。选出参的理由：递归调用
  里"返回结果"要靠每层手工合并，出参天然累积，局部性更好。
- **`main()` 的退出码契约**：`0` = 请求的每个包都在闭包里；`1` = 有未解析项（逐条点名）；
  `2` = 环境/读索引失败。与 `--list-compatible` 无关（那条恒 0）。
- **零值守卫**：`plan` 为空且请求了包 ⇒ 退出 1（哪怕"请求的包"恰好都在 `SKIP_DEPS` 里 ——
  那种情况显式报"请求的包全是内建依赖，闭包为空"）。
- **下载逻辑本身不改**：sha256 校验、`cached` 复用、失败时不删已下载件，全部照旧。
  ★ 但**解析失败时不再往下下载**（旧行为是"能解析的先下"）—— 这是有意收紧：
  半套下载既没用（下游必须整体重跑）又白花带宽；已下载件仍在缓存里被 `cached` 路径复用。
- **不改输出格式**：成功路径的每行格式**逐字不变**（`name` / `id` / `status` / `size` / `依赖[]`），
  只新增失败时的汇总段。
- **`forge-build.sh` 加 `set -e` 或显式检查**：fetch 非零 ⇒ 立刻退出，不解析不打包。
  取最小改法：在那行调用后加 `|| exit 1`（`set -e` 会连带改变其它行的行为，风险更大）。

## Testing Decisions

**测试缝 = `forge-fetch.py` 的 `--selftest`（新增），它走的是进程退出码这条最高缝。**

理由：这个缺陷的全部危害都在"退出码骗人"，所以判据就该是退出码 + 点名内容，
而不是内部函数返回值。`--selftest` 内部用**夹具索引**（不碰网络）调用同一套
`resolve`/`main` 逻辑。

三类用例齐备（本仓 F1 纪律）：

| 类 | 用例 | 判据 |
|---|---|---|
| 正常 | 请求 1 个存在的包，索引里有兼容版本 | rc=0，闭包含该包 |
| 反向 | 索引里没有该包 | **rc≠0** 且 stderr 点名该包 |
| 反向 | 有该包但无兼容版本 | **rc≠0** 且点名"无兼容版本" |
| 反向 | 请求 2 个包，其中 1 个失败 | rc≠0（不许因"另一个成功"而放行） |
| 空输入 | 请求的包全在 `SKIP_DEPS` | **rc≠0** + 明说"闭包为空" |
| 零值 | 请求 0 个包（`--octave` 但无包名） | 维持现有的 `ap.error`（rc=2） |

**先看别的闸门怎么写的**（prior art）：
`build/113/provision-omc.sh --selftest` 与 `build/113/check-ci-bootstrap.sh --selftest`
都是"临时目录 + 夹具 + 三/四类用例 + `=== N PASS / M fail ===` + 非零退出"的形状，
本件的自证照抄这个骨架。

**变异测试**（证明它真会红）：把 `main()` 的 `return 1` 改回 `return 0`，
`--selftest` 必须变红。这条写进 spec 的结案判据。

## Out of Scope

- **不修 GitRoll 的其余 930 条**。它们分三类，各有归属判断：
  - `var` 363 条（`bridge/`、`site/` 的 ES5 兼容胶水）—— **改 `let` 会让老浏览器崩**，
    这是**有意为之**，不修（在 issue 里留证据说明）；
  - 深层嵌套 62 条、cognitive complexity 若干 —— 是**可读性债，不是缺陷**，单独立项；
  - 安全漏洞 1 条（`build/embed/coi-serviceworker.js`）—— **第三方库**
    （`coi-serviceworker v0.1.7`, MIT, Guido Zuidhof），不归我们改，只在 issue 记录来源。
- 不改 `forge-fetch.py` 的版本选择算法（`pick_version`）。
- 不引入 `--strict` 之类的新开关：失败就是失败，不需要"可选严格"。
- 不重构 `forge-build.sh` 的其它步骤。

## Further Notes

**为什么 GitRoll 这条值得修（哪怕它措辞笨拙）**：它指的位置（`resolve` 行 103）
恰好是三条静默路径的入口。措辞"always return the same value"描述的是**表象**，
但**判据落点是对的**。我起初判它误报，是看漏了 `main()` 不看返回值 —— 用户纠正。

**与 GitRoll 的一次性说明**（写进 issue #7 的评论，不是 dismiss）：
其余 930 条要有归属分类，否则下一轮扫描还会重复"谁该修这些"的讨论。
特别要让扫描方知道：`var` 那 363 条是**兼容性要求**，不是疏漏。
